# 운영 점검·밸런스 분석 도구 설계 · 2026-10-22

사용자가 실시간 PvP 플레이 봇보다 우선하도록 변경한 목표다. 이전 PPO 모델·로그는 보존하고
자율적인 플레이 봇 학습은 중단한다. 이 도구는 매일 두 번 서비스 상태와 게임 밸런스를
점검하고 근거가 있는 패치 후보를 시뮬레이션·보고·PR로 제공한다. 아직 운영 자동 배포를 승인받은 것이 아니다.

## 사용자가 정한 난이도 곡선

| 경험/목표 | 의도한 진행 |
| --- | --- |
| 첫 플레이 | 10–15웨이브 도달 |
| 2–3판 학습 후 | 20웨이브 달성 |
| 중수 | 30웨이브 달성 |
| 40웨이브부터 | 물약과 고도의 전략을 활용해야 달성 |

이는 사용자 의도이며 아직 수치화한 인구별 달성률 목표는 아니다. 초보자를 무작위 행동과
동일시하지 않는다. 초보/학습/중수/숙련 정책군 및 실제 익명화 코호트로 검증한다.
최신 추가 요구는 궁수 단일 전략이15웨이브를 넘기지 못하고 상위 포탑/문명 전환이 필요해야 한다는 것이다.
이전 궁수20허용 기준은 폐기한다. [문명 전환 검증](reports/2026-10-22-civilization/README.md)에
솔로 중장갑 화살 저항 패치와새20시드 결과를 기록했다. 아직 운영 배포는 하지 않았다.
기존10개 시드에서 궁수전략이 교란병 포탑파괴66회·재건설46회를 겪고20을 달성한 것은
20까지의 자동 정책 표본일 뿐, 초보 난이도나30/40밸런스의 증거는 아니다.

## 서로 다른 두 분석 경로

### 운영 상태

- 공개 GET /game/, /game/balance.js, /game/game.js, /api/clan 을 저빈도로 점검한다.
- HTTP 상태/실패/개별 응답 시간/캐시·소스 해시/GET API의 ready 상태를 기록한다.
- GET /api/clan은 소스상 DB SELECT 1과설정 확인이다. 성공해도 실제 방 생성/로그인/WebSocket/
  전투 명령의 정상 동작을 보장하지 않는다. HTML200만으로 서버 정상이라고 판단하지 않는다.
- 실제 이용자 지연/동접/끊김률/장애 지속 시간은 별도 집계 로그가 있어야 한다.
  PC 한 지점의 소수 GET 응답 시간을 전체 사용자 p95나서버 CPU로 해석하지 않는다.
- 로컬 네트워크 오류는 관측 실패이며 사이트 전체 장애로 단정하지 않는다.
- 하루 두 번은 정기 점검이다. 두 점검 사이 장애를 즉시 탐지하는 상시 관제가 아니다.
  상시 경보가 필요하면 별도 지속 수집/상태 저장이 필요하며 배포는 추후 검토한다.
- 기존 check-live-http.mjs는 방 생성/가입/전투 명령을 수행하므로 읽기 전용 정기 점검에서 실행하지 않는다.
- latency, Server-Timing, X-Clan-Queries/Retry 및 Worker observability 설정은 소스에 있으나
  이미 이용자 전체 장기 통계가 수집되고 있다고 주장할 수 없다.

### 게임 밸런스

1. 매 실행마다 배포 파일·현재 Git의 엔진/밸런스 해시를 비교하고 어떤 버전을 시험했는지 명시한다.
   로컬/사이트 버전이 다르면 로컬 결과를 현재 라이브 밸런스의 결과라고 부르지 않는다.
2. 실제 엔진에 다양한 전략/실수/자원 운용 정책을 넣어10/15/20/30/40웨이브를 측정한다.
3. 물약 사용/미사용, 단일 포탑/조합, 경제 투자, 재건설/수리 등 대응 정책을 대조한다.
4. 실제 플레이 로그가 있으면 첫판/2–3판/중수/숙련 코호트를 비교한다. 실력·패치 버전·사용 위치·
   도달 단계로 나누지 않은 단순 이용률/승률로 시설을 너프하지 않는다.
5. 후보는 처음에는 한 그룹에서 한 요소만 작은 폭으로 바꾼다. 예: 비용 또는공격 간격5–10%.
   후보 파일은 ml 아래의 격리 공간에만 두고 라이브/원본 balance.js를 직접 수정하지 않는다.
6. 같은 정책/게임 시드/예산에서 기준과 비교하고, 고정 검증 시드와 별도 정책군에서 다시 확인한다.
7. 사용자 목표에 가까워지고, 다양성/자원 병목/실행 비용/다른 모드의 회귀가 허용 범위인지 판단한다.
   근거가 없으면 패치 없음이 정상 결과다. 매일 두 번 패치할 필요는 없다.

## 전역 시설의 검증 범위

| 그룹 | 검증할 변수와 역할 |
| --- | --- |
| 궁수/발리스타/폭격포/서리/번개 | 비용, 해금 문명, 사거리/공격력/간격, 강화 비용, 쌍발/관통/폭발/감속/연쇄와 조합 |
| 성 | 강화 비용, HP증가, 공격 보정, 문명 해금 시점과 생존/경제의 상충 |
| 광부/벌목꾼 | 고용 비용/상한, 생산 주기, 크리스탈 확률, 이동·벌목 시간, 투자 회수 시점 |
| 수리 | 나무 비용 증가, 회복량, 위기 대응 가치, 반복 수리 악용 여부 |
| 연구소/물약 | 건설/연구 비용과 대기, 사용 비용/쿨다운, 천둥의 현재HP비례 효과, 얼음 정지/제어 효율 |
| 적/웨이브 | 구성, HP·속도 증가, 동시 웨이브 위험/시간 이득, 교란병 파괴 확률/재건설 부담 |
| PvP 전용 | 훈련소/군사/공격 연구·물약/침공·디버프, 상대 대응·진영 편향·통신 비용 |

현재 public/game/balance.js에서 조정 가능한 것은 시작 자원/웨이브 휴식/5종 포탑의
gold/damage/rate/range다. 물약·경제·강화·적·해금 등은 game.js에 하드코딩된 부분이 많다.
따라서 전역 최적화는 아직 지원되지 않는다. 후보 스키마와 샌드박스 주입/원본–서버 일치 검사를 먼저 만들어야 한다.
생성본 lib/game-engine.js만 고치면 안 된다. 원본과서버·클라이언트의 규칙 동기화가 필요하다.
현재 ML브리지는 혼자하기이고 PvP 전용 시설 행동을 모두 제공하지 않는다. 별도 매치 시뮬레이터가 필요하다.

## 사용할 알고리즘

- 운영 경로: 임계값/추세/이상 탐지. 이 문제에 PPO를 사용하지 않는다.
- 초반 밸런스: 전략군 + 같은 시드 대조 + 작은 구간 탐색/실험 설계.
- 데이터가 쌓이면 파라미터→진척/다양성/경제 결과를 예측하는 대리모델과 베이지안 최적화 검토.
  초기에는 수십 개 결과로 신뢰할 ML모델이 완성됐다고 주장하지 않는다.
- PPO는 선택적인 스트레스 테스트 정책이다. 새 밸런스에 기존 모델이 적응하지 못해 성적이 떨어진 것을
  난이도 개선이라고 판정하지 않는다. 정책을 재학습하거나 여러 고정 정책과함께 검증해야 한다.
- 목적은 모든 조합의 승률을 같게 만드는 것이 아니라 역할 차이/선택 이유/난이도 곡선을 유지하는 것이다.
- 패치 목적함수 가중치/인구별 달성률·최소 표본 기준은 초도 자료 후 구체화한다.

## 필요한 실제 데이터와 현재 빈틈

현 스키마는 랭킹/계정 진행 최고치·일부 누적 기록/피드백/방 스냅샷을 가진다.
모든 전투의 시설별 행동·피해·사용률·실패/이탈 사유·경험 판수·패치 버전 시계열은 확보되지 않았다.
개인/세션/키/IP 원문을 저장하거나 보고서에 넣지 않고 서버 기준 익명 집계를 사용해야 한다.

필요한 데이터 계약:
- 패치/엔진 해시, 모드/게임 시드, 시작/종료 시각, 실제 완료 웨이브, 종료/연결 종료 사유.
- 경험 판수 구간(첫판/2–3판/그 이후), 시설별 건설/강화/파괴/재건설, 경제 투자/수리.
- 물약 연구/사용/자원 부족·사용 기회, 적 처치/누수/피해, 잔여 자원·HP.
- 익명 집계 명령 RTT/서버 처리 시간/재접속·서버오류율, 집계 구간/분모/누락률.

이 수집을 위해 운영 계측 변경이 필요하면 소스·스키마·부하/보관 기간을 별도 PR로 검토한다.
현재 단계에서 운영 DB/Cloudflare 로그를 읽을 수 있는 권한이나연결이 확보됐다고 가정하지 않는다.
읽기 전용 집계 로그/피드백 export 또는명시적으로 허용된 읽기 도구가 필요하다. 비밀키를 대화에 붙여넣도록 요청하지 않는다.

## 정기 실행과 단계

한국시간09:00/21:00을 기본 일정으로 사용한다. 기존2시간 간격 PPO 자동화는 이 업무로 전환한다.
로컬 실행은 PC/앱의 실행 상태에 의존한다. 사이트에상주하는 학습 봇이나24시간 운영 서비스는 아니다.
상태 변화/장애 의심/의미 있는 새 결과/사용자 결정이 필요할 때만 알리고 같은 보고를 반복하지 않는다.

1. 이번: 설계/시설 인벤토리/난이도 기준, 낮은 부하의 읽기 전용 공개 상태 수집기.
2. 다음: 현재 배포 엔진 확인, 궁수전략의30/40 도달과 숙련도별 정책군, 물약/조합 대조.
   실행당 오프라인 시험 CPU1스레드·약10분 이하, PPO학습/실제방 생성/부하 시험은 하지 않는다.
3. 이후: 격리 후보 주입/후보 탐색·검증 및 근거가 있는 패치 PR. 첫 판/반복 플레이 자료 부족은 명시한다.
4. 실제 이용자 로그와상시 관제 연동은 별도 검토. 소스 테스트와원본/서버 일치 검증 후 배포는 사용자 확인 단계다.

기존 main 병합·운영 DB/PvP/Cloudflare/Sites 변경 금지와OpenAI API/유료 자원 미사용 조건을 유지한다.
